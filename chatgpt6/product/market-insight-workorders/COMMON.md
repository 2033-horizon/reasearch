# 执行 agent 统一约定

需求源：[市场洞察 Agent PRD](../market-insight-agent-prd.md)。派发入口：[工单总览](./README.md)。每张工单和本文件共同构成执行任务，不需要重新猜测整个项目目标。

## 1. 范围和现状

当前项目是 GPT Researcher，沿用 Python/FastAPI 与 Next.js。工单中的新增模块/测试/API 是实施目标，不代表已经存在；“已有”文件链接指向拆单时检查过的源码。阅读实际代码后再编辑，不能只根据路径名推断行为。

本文档和代码链接均使用相对路径：Markdown 链接相对于所在文档；代码标识中的 `gpt_researcher/...`、`backend/...`、`frontend/...` 等路径相对于仓库根目录。保留这种可迁移写法，不写开发机盘符。

本套工单默认交付可评审代码、验证证据和交接说明。生产部署、服务采购和对外发送通知不属于 P0 拆单的默认动作。若用户在执行时明确调整范围，以该次有效指令为准并记录变化。

## 2. 开工检查与依赖

1. 阅读适用的仓库指令、当前 PRD、目标工单和已有契约；检查 `git status`，保留他人工作。
2. 确认工单的硬前置在本工作目录中真实可用，读取前置交接和接口版本；不能凭存在一个同名文件就判为实现完成。
3. 依赖缺失时列出具体缺失对象、调用签名或验收项；可以推进独立部分，但不得用空实现或第二套 schema 替代前置后宣称完成。
4. MI-002 冻结 `schemas.py`、`ports.py`、前端类型及 `docs/product/market-insight-contracts.md`。之后对契约的新增应兼容，破坏性调整需协调受影响工单并同步文档/验证。
5. 当 PRD、工单与现有实现出现冲突，报告具体差异并做最小必要修正，不擅自降低证据或发布标准。

执行时自行选择合理实现细节，复用当前版本的库和项目习惯。常规设计选择无需反复请用户批准；真实业务输入不足与可以自行实现的技术选择要区分。

## 3. 必须保持的业务约束

- 发布主体类型、来源等级、证据质量与主张采纳是不同对象。域名/知名机构/模型评分不是自动通过理由。
- A 单证据必须满足 PRD §6.3 所有条件，包含已执行并可追踪的冲突/更正检查；未检查不能写成“未发现”。
- 至少两条 B 证据只有在原始生产链独立、口径可比且直接支持时才可交叉采纳。多条 C 一致不升级为事实。
- 转载、镜像、共用数据库不能虚增独立来源数；未知关系保持未知。
- 原文必须在上下文筛选前保存，数据不能仅来自摘要、LLM 记忆或模型生成图片。
- 数字、单位、期间、主体、区域、口径、预测标签与原文定位不可丢。未知值不填零。
- 已采纳证据为空时返回不足，不能利用现有 `ext_context or self.researcher.context` 回落到未核验材料。
- 草稿/模型自评/达到修改次数上限都不等于通过。异常、超限、未知与冲突有明确出口，不自动 `accept`。
- 报告事实只取冻结的已采纳证据；争议区仅准确引用来源表述，不伪造统一值；未通过的事实不能进入“合格部分报告”。
- 计算由程序执行，分析判断列依据与假设；报告数字/图表/摘要/附录和追问都需要一致的支持检查。
- 旧报告和新报告不得共享被静默覆写的核验结果；修订生成新版本并保留影响关系。
- 所有新 API、证据快照和下载必须使用同一身份/权限边界，不能靠前端隐藏按钮保护数据。

## 5. 并行修改和共享文件

建议每个并行 agent 在已包含前置提交的独立分支/工作树执行。若共享目录，只编辑本单负责的文件，不回滚他人改动。多个 agent 不应同时改一个入口文件；文件责任和集成安排如下。

| 共享文件/边界 | 初始负责方 | 后续修改顺序或规则 |
| --- | --- | --- |
| `schemas.py`、`ports.py`、`types/market-insight.ts` | MI-002 | 兼容扩展需同步契约，按指定负责人串行修改，不复制临时第二份 |
| `backend/server/app.py` | MI-004 | 注册一次 insight 总 router；其他组件输出独立 router，不各自改 app.py |
| `backend/server/insight_routes.py` | MI-004 | MI-009 注册基础模块 → MI-018 接复核/报告 → MI-023 接最终聊天/导出 |
| `workflow.py` | MI-009 | MI-014 接完整证据链 → MI-018 接报告准入 → MI-023 最终运行联调 |
| `verifier.py` | MI-009 | MI-013 扩展完整决策，二者不能并行改同一文件 |
| collector 注册/组合 | MI-006/MI-009 | MI-011 输出独立解析器，MI-014 统一注册，P1 扩展另按实际排期 |
| `app/insight/[id]/page.tsx` 与公共 UI 请求层 | MI-019 | MI-020/021 交付独立面板，MI-023 挂载；不重复实现客户端状态 |
| `pyproject.toml` / requirements / package manifest / 锁文件 | 当轮集成负责人 | 组件说明所需依赖及理由，由负责人统一加入，避免各分支全面升级 |
| 全局配置/部署入口 | MI-023 | 开发测试配置限定本模式，不改普通研究默认值 |
| 公共 fixtures 与最终验收集 | MI-001 / MI-024 | 组件使用自己的子目录；不能改公共预期值来适配错误实现 |

路径范围是职责边界，允许因实际代码结构做合理的小幅调整并在交接解释。若确需修改共享文件，先与同批执行者/集成负责人协调写入顺序；这不等于要求用户逐项审批代码改动。

子工单的独立 router/面板可先在测试应用中验证。未挂入实际应用时状态应反映待集成，不宣称用户路径已可用；集成责任单不得遗漏注册步骤。

## 6. 验证规则与完成定义

工单列出的测试路径为拟新增位置，当前不一定存在。实施者使用现有 pytest/前端构建工具，针对数据错误、越权、超限、状态和跨模块行为编写必要测试，不为薄封装或 getter 重复堆砌测试。

建议命令仅作入口参考，须在目标目录实际运行并报告结果：

```text
仓库根目录：
python -m pytest tests/market_insight/<本单行为测试文件>.py

frontend/nextjs：
使用当前项目选定的包管理器执行类型检查和 build；
已有 lint 脚本可用时执行，记录基线环境问题。
```

没有 API Key 时，先用冻结 fixture 和受控 provider 验证规则；不得使用模型网络异常作为“默认通过”的原因。真实检索召回、写作质量、成本、部署身份及人工节省，需要在相应环境中实测；没有运行就写“未测”。

一张工单达到交付要求时，应满足：

- [ ] 目标代码已实现，不是只写建议、TODO、接口空壳或模拟成功响应。
- [ ] 输入输出与冻结契约一致，必要迁移/配置有说明。
- [ ] 工单的业务正例、关键反例和权限/失败条件得到验证。
- [ ] 影响到的现有路径完成适当回归；不为了达标删除测试或降低规则。
- [ ] 共享文件改动和集成挂载责任明确；未集成部分如实标记。
- [ ] 必要说明和样例已更新，新增真实链接用相对路径。
- [ ] 使用下面的交接模板记录实际结果及未完成项。

测试失败后修复并重跑受影响检查，成功后不无理由反复全量运行。正式报告/数据产物还需相应视觉或人工核对；成功生成文件不等于内容和排版通过。
